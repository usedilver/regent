# Regent v2

Contrato de producto vigente, actualizado el 2026-09-08.
Este documento prevalece sobre el [historial de arquitectura](v2-history.md).
Describe el objetivo acordado; la seccion de estado distingue lo implementado.

### Recuperacion de conexion Slack (2026-09-08)

La reconexion posterior al arranque esta supervisada por Regent: un fallo de
`apps.connections.open` no debe terminar el proceso ni las ejecuciones activas.
Se desactiva la reconexion interna de socket-mode 3.0.1, cuyo callback puede
dejar rechazos sin capturar, y se reintenta sin concurrencia con esperas de
5 a 60 segundos. El timeout HTTP de Slack es de 10 segundos por intento.
La salud indica `slack_connected: false` hasta recibir `connected`; cerrar el
servidor cancela reintentos y drena la conexion pendiente antes de desconectar.
Los errores del arranque inicial siguen siendo explicitos y detienen el inicio.
Pruebas automatizadas: caidas repetidas, recuperacion, eventos duplicados y
cierre durante espera/reconexion. Pendiente: corte y restauracion real de red.
No se garantiza recuperar eventos que Slack no entregue durante una desconexion.

Regent es un cliente conversacional open source para ejecutar Claude Code CLI.
Slack es su primera interfaz. No es un framework de backlog ni un flujo de
desarrollo obligatorio. No depende de Talently, una organizacion, un tracker,
una plantilla o un proveedor de despliegue.

## 1. Configuracion minima

El operador configura autenticacion, acceso a Slack, workspace y repositorio
predeterminado. No necesita mantener un catalogo de dominios o proyectos.
Ejemplo de las opciones de contexto existentes:

```yaml
repos:
  path: /absolute/path/to/projects
  default_repo: team-context
```

`default_repo` es relativo al workspace efectivo (`path` mas `workspace_root`,
si se configura). Es el contexto inicial de una conversacion nueva sin otro
proyecto indicado. No limita los proyectos que el agente puede atender.
Las conversaciones existentes conservan su contexto hasta cambiarlo.

## 2. El repositorio manda

Cada repositorio aporta sus instrucciones (`AGENTS.md`, `CLAUDE.md`), skills,
MCPs, reglas, variables y scripts. Regent debe cargar el contexto usando las
capacidades del runtime, no duplicar esas instrucciones en un contrato propio.
Las credenciales del servidor no deben filtrarse a los procesos de los proyectos.

Las reglas de negocio, el enrutamiento de URLs a subproyectos, las plantillas y
el proceso de publicacion pertenecen al repositorio. Un repo padre puede aportar
contexto para trabajar sobre sus submodulos; no hay que copiarlo a Regent.

Regent conserva controles operativos: usuarios autorizados, limites de ejecucion,
cancelacion y aislamiento de sesiones. No debe imponer gates de producto.
Respetar permisos nativos y usar `bypass` no son equivalentes: el modo actual
`bypass` no aplica las decisiones nativas `allow/ask/deny` como `native`.
Los hooks de Regent no constituyen un sandbox de seguridad.

## 3. Multiples proyectos

El usuario puede pedir crear proyectos, clonar repositorios o revisar GitHub.
Una consulta remota no exige clonar si las herramientas disponibles bastan.
Para crear o clonar, el agente utiliza las herramientas e instrucciones del
repo de contexto, dentro de los permisos y directorios autorizados.

Si se indica un proyecto, debe seleccionarse y cargar su contexto antes del
trabajo sustantivo. Si solo se indica una URL, el contexto del repo por defecto
puede resolverla mediante sus propias instrucciones. Se pregunta al usuario
solo cuando no se puede resolver el destino o hay una ambiguedad relevante.
Un `cd` de shell no equivale a recargar settings, MCPs y sesion del runtime.

No se requiere `.regent/projects.json`. El manifiesto de perfiles introducido
anteriormente fue retirado del runtime, no es una nueva obligacion
para los repositorios. Regent no necesita guardar dominios, plantillas ni comandos
de provisioning en un formato propio. Si persiste un cwd o una sesion, eso es
estado operativo, no un catalogo que el usuario deba mantener.

## 4. Solicitudes abiertas

Preguntas, investigacion, bugs, features, invocacion de skills y creacion de tareas
son solicitudes validas. No toda conversacion es una tarea de desarrollo.
Jira, Notion u otro tracker se usan cuando el usuario lo solicita y el proyecto
los tiene configurados. No son requisitos de arranque ni dependencias del core.

El usuario y el repo determinan si hacen falta plan, aprobacion, tests, PR o
despliegue. Regent garantiza aislamiento Git por conversacion con worktree y rama
propios, como control operativo. No debe imponer tamanos S/M/L, cards ni gates
universales para ejecutar una solicitud. Pedir una sala tampoco exige un card.

## 5. Conversaciones

Se puede conversar por DM o en hilos de Slack. En canales compartidos el agente
interviene por mencion, salvo respuestas a sus preguntas y controles de sesion.
Debe poder ser detenido, corregido y reanudado, y hacer preguntas u ofrecer
opciones en la misma conversacion.

En cada intervencion debe incorporar los mensajes relevantes nuevos del hilo,
incluidos los de otras personas, sin duplicarlos. Reanudar la memoria de Claude
no basta: esa memoria no contiene los mensajes de Slack que nunca se le enviaron.

## 6. Salas opcionales

Cuando se le pide, el agente puede crear una sala/canal y trasladar alli la
conversacion conservando objetivo, decisiones y trabajo pendiente. El origen
debe apuntar a la nueva ubicacion. No requiere tarea local ni tracker externo.

En la sala se usa el contexto relevante del canal y sus hilos al intervenir,
respetando los controles de acceso. No significa responder automaticamente a
cada mensaje del canal. La continuidad debe sobrevivir a reinicios del servidor.

### Aceptacion

1. Pregunta abierta en DM: usa el repo por defecto y no crea tarea ni sala.
2. Correccion de bug: sigue reglas y permisos del repo, verifica el resultado y
   publica solo conforme a la solicitud y al flujo del repo.
3. Crear, clonar o revisar otro proyecto: resuelve el destino sin manifiesto
   obligatorio y carga el contexto adecuado cuando trabaja en el nuevo repo.
4. Cinco mensajes de otras personas entre menciones: la siguiente intervencion
   conoce esos mensajes; interrumpir, corregir y responder opciones conserva contexto.
5. Solicitar una sala: traslada la conversacion y usa mensajes nuevos del canal,
   sin crear una tarea como efecto secundario.
6. Solicitar una tarea: usa el tracker configurado por el repo; sin solicitud
   no crea un card. Sin tracker disponible explica el limite o pregunta.

### Avance 2026-09-07: proyectos sin manifiesto

Retirados `regent_project_profiles`, `regent_create_project` y su ejecutor de perfiles.
La seleccion de repo conserva validacion del workspace y handoff persistido, sin
depender de efectos de provisioning. Git/gh usan los permisos del runtime, igual
que scripts y otras herramientas; ya no existe una prohibicion global de escritura.
En bypass esto no constituye aislamiento de shell ni enforcement de permisos nativos.

Pruebas: clon local real, repo sin commits, worktree con `.git` como archivo,
rutas invalidas y symlinks externos, handoff con entorno nuevo y catalogo MCP sin
las herramientas retiradas. Suite completa `pnpm test`. No se crearon recursos
remotos ni se probo aun este flujo con Claude/Slack reales.
Ese modulo dejo pendiente retirar gates de negocio y restricciones de edicion.
Detalles y migracion en [projects.md](projects.md).

### Avance 2026-09-08: flujo definido por el repo

Retirados del runtime los helpers de tareas, worktrees, instalacion, tests y PRs,
las compuertas plan/QA, el polling de merges y el webhook GitHub. La CLI conserva
`ask`, `patch`, `runs` y `tail`; el MCP interno solo contexto, progreso, preguntas
y cancelacion. Eliminadas las skills incluidas de plan, implementacion y QA.

Write/Edit/NotebookEdit admiten rutas del workspace sin tarea ni worktree previo,
validando symlinks y conservando filtros de credenciales. El workspace se pasa
como directorio adicional del runtime. En modo nativo ya no se preautorizan las
herramientas de edicion: decide la configuracion del repo. En bypass no hay esas
reglas nativas ni aislamiento automatico entre conversaciones que editan lo mismo.

`policy` antiguo se acepta pero no se ejecuta. Tablas historicas permanecen en
SQLite; no se reanudan gates ni se publican o limpian sus recursos automaticamente.
Los tests del flujo retirado se sustituyeron por pruebas de edicion y commit locales
sin tarea, politica antigua sin efecto, seleccion de repo y catalogo MCP reducido.
Se conservan pruebas de sesiones, cola, preguntas, cancelacion y autorizacion.
`pnpm test` pasa; no se ha validado aun con un modelo real en Slack ni se ha publicado
un PR real durante esta revision. Las pruebas nativas verifican argumentos y politica
de Regent, no simulan el motor completo de permisos de Claude.

Siguiente: historial incremental de Slack en cada intervencion; despues, salas
independientes. Estos dos puntos siguen pendientes, no forman parte de este cambio.

### Correccion 2026-09-08: concurrencia

La retirada anterior del aislamiento fue una regresion: compartir un checkout
permitia mezclar cambios entre conversaciones. Se restauro sin tareas ni gates.
Cada repo/conversacion tiene un nombre estable de worktree nativo; Regent conserva
el repo fuente como contexto y limita ediciones y cwd de comandos al directorio
propio. No se concede --add-dir al workspace entero. Salir del worktree mediante
EnterWorktree/ExitWorktree se rechaza: los cambios de proyecto usan regent_use_repo.

Requiere Claude Code >=2.1.263 (version local comprobada); una version anterior no
se ejecuta sin aislamiento. La verificacion se basa en las capacidades de
[worktrees nativos de Claude](https://code.claude.com/docs/en/worktrees).
Git worktrees no son un sandbox para scripts/MCPs ni aislan servicios externos.
Un hook WorktreeCreate con ubicacion diferente y un repo sin commits pueden impedir
el arranque aislado; no se permite fallback al checkout compartido.

Pruebas locales: dos conversaciones activas con directorios/ramas separados,
rechazo de ediciones cruzadas y cwd compartido, commits sin afectar al original,
dos worktrees de un submodulo y flags de worktree/resume. `pnpm test` pasa.
La suite usa Git real y un runner simulado; falta smoke con Claude real y Slack.
Las notas anteriores sobre edicion compartida quedan sustituidas por esta correccion.

### Avance 2026-09-08: contexto incremental de Slack

SQLite v5 guarda la fuente de contexto, una captura por ejecucion y las versiones
de mensajes entregadas a cada sesion. La deduplicacion ocurre al ejecutar, despues
de los turnos anteriores de la cola. El resultado del run y la confirmacion del
contexto se persisten en la misma transaccion. Un fallo de API no consume contexto;
una interrupcion puede repetir contexto incierto al reanudar, pero no lo descarta.

Cada mencion incorpora mensajes de otros miembros, adjuntos y cambios de texto.
Se evita repetir el mensaje que dispara el run y se conservan sus adjuntos. Los
eventos message/app_mention se identifican por canal/timestamp. Una sesion nueva
recibe otra vez el contexto completo, incluidas respuestas anteriores del bot;
una sesion reanudada no reinyecta las respuestas propias ya presentes en su memoria.
Respuestas por botones y continuaciones internas usan la fuente persistida.

En canales se consultan tambien respuestas a raices antiguas; no basta avanzar
un timestamp del canal. Esta primera version pagina el historial relevante completo
y hace incremental el contexto enviado, no el trafico de la API. Las capturas se
acotan al timestamp de la mencion. Limites: 2000 entradas y 200000 caracteres de
captura; se informa el exceso o errores de permisos sin continuar con contexto
silenciosamente incompleto. No se sintetizan avisos de mensajes eliminados de Slack.

Pruebas: cinco mensajes intermedios, menciones solapadas en cola, eventos repetidos,
ediciones, adjuntos, paginacion de canales y respuestas antiguas, reinicio con cola,
sesion nueva, fallo de consulta y cancelacion. Suite `pnpm test` incluida.
Pendiente validacion end-to-end real de historial y salas independientes.

### Avance 2026-09-08: salas independientes

`regent_create_room(name, summary, users)` crea un canal privado solo a peticion
del usuario. Invita al solicitante y a los IDs explicitos de miembros del workspace;
no invita automaticamente a todos los participantes del origen. No crea tareas
locales, cards, planes ni nuevos worktrees. Los permisos de uso del agente siguen
dependiendo de la configuracion del operador, no de ser miembro de la sala.

SQLite v6 conserva un registro operativo `room_transfers` por conversacion:
nombre estable con sufijo, canal, origen, resumen, invitados y estado del traslado.
No es un manifiesto de proyectos ni una configuracion adicional del repo.
Si Slack crea el canal pero se pierde la respuesta, el reintento lo busca por ese
nombre y verifica que pertenezca al bot. Si falla una invitacion, no traslada la
conversacion: el siguiente intento reutiliza la sala y completa las invitaciones.
Una solicitud repetida reutiliza la misma sala y permite agregar invitados.

El cambio de destino, historial de canal, runs activos/en cola, preguntas pendientes
y avisos se guarda en una transaccion. Se conservan clave, sesion Claude, cwd y
aislamiento Git. Se cierra el stream del origen y las respuestas siguientes van
al destino. Nuevas menciones en el origen reciben el enlace; alli no se abre otra
ejecucion ni se detiene la sala desde un control antiguo. En la sala se mantiene
la regla de mencion y se incorporan los mensajes relevantes del canal y sus hilos.

Los avisos pendientes se entregan tras reconectar o reiniciar. Una creacion o
invitacion incompleta se retoma cuando se reintenta la solicitud; no se reinicia
Claude automaticamente tras una interrupcion. La entrega de mensajes a Slack es
al menos una vez: una respuesta perdida despues de publicar podria repetir un
aviso, aunque no se vuelve a encolar el traslado ni se crea otra sala por ello.
No se archivan canales ni se eliminan worktrees automaticamente.

Pruebas locales: traslado desde DM/hilo, continuidad de sesion y worktree,
destinos en cola, preguntas y botones, invitacion fallida, respuesta de creacion
perdida, cancelacion, reinicio y entrega durable. Suite `pnpm test` con Slack
simulado. Pendiente el flujo real completo; siguiente bloque: onboarding minimo
y seleccion explicita de repositorio al iniciar la conversacion.

### Avance 2026-09-08: setup minimo y seleccion inicial

`pnpm regent setup --repo <ruta> --team <ID> --user <ID>` crea solamente el YAML
del operador. Deriva el workspace de la carpeta padre; `--workspace` permite
definir una raiz mas amplia. No requiere catalogos de proyectos ni archivos
Regent en los repos. No sobrescribe configuraciones, no guarda tokens y no abre
la base de sesiones. Conserva modos indie/team y bypass/native con sus avisos.

En una conversacion nueva, `repo: ruta` en la primera linea o `--repo` en CLI
selecciona el cwd antes de iniciar Claude: carga directamente entorno, contexto
y aislamiento del repo indicado. Rutas inexistentes o fuera del workspace fallan
sin crear la conversacion ni ejecutar en el default. Sin selector, se conserva
el contexto actual o se usa el predeterminado al iniciar.

La sintaxis no es obligatoria para usuarios de negocio. Nombres de proyectos,
URLs y dominios siguen resolviendose con las instrucciones y capacidades del repo,
no mediante heuristicas ni un registro de Regent. En una conversacion existente,
un selector diferente pide al agente usar `regent_use_repo` antes de trabajar,
con handoff y nueva sesion; el cambio depende de esa llamada del modelo. No se
reconfigura un proceso activo ni se pierden sus mensajes en cola.

Pruebas: setup sin credenciales/DB, configuracion existente intacta, modos y rutas,
seleccion inicial con entorno y worktree correctos, eventos duplicados y cambio
solicitado en una conversacion existente. Pendiente validacion real de los seis
flujos de aceptacion en Slack; es el siguiente bloque para cerrar v2.

### Correccion 2026-09-08: progreso y cierre por tiempo

La prueba real de comparacion en una sala mostro dos ACK identicos y un timeout
tras 600 segundos. El run seguia ejecutando herramientas; el silencio no era
evidencia de bloqueo. Los ACK provenian del fallback de dos actualizaciones de
estado y el mensaje final repetia la instruccion de continuar entre runner y core.

Integrados los cambios locales de progreso con estas correcciones:

- El indicador nativo requiere confirmacion de Slack, no solo un thread_ts.
  El fallback se evalua despues de enviar el estado, en cada tick y tras un traslado.
- Un mensaje de progreso por run se actualiza en el mismo lugar. SQLite v7 guarda
  su canal y timestamp; la limpieza se reintenta tras reinicio o fallo de borrado.
  No se olvida el identificador hasta confirmar el borrado o message_not_found.
  No hay garantia exactly-once si Slack publica pero se pierde la respuesta antes
  de guardar el timestamp; las actualizaciones periodicas no se encolan para replay.
- Las salas Regent son canales privados normales. La API nativa admite hilos en
  canales/DMs y canales de sesion, pero estos ultimos no son los que crea Regent.
  Fuente: https://docs.slack.dev/reference/methods/agents.sessions.setStatus/
- El turno reserva min(60 segundos, 20% del limite) para cerrar. El prompt incluye
  el plazo UTC, se avisa a Slack y la politica rechaza nuevas herramientas durante
  ese margen indicando que entregue hallazgos parciales. Se conservan comunicacion,
  cancelacion y recogida/parada de subagentes existentes. No se amplian los limites.
- Si el proceso termina interrumpido, se muestra el texto disponible como parcial,
  no como tarea completada. Si no existe texto, se dice expresamente. Una llamada
  ya en curso puede agotar el margen; no se garantiza resumen ni continuacion sola.

Pruebas automatizadas: status rechazado, ACK no duplicado, actualizacion in-place,
traslado durante el run, reinicio, borrado fallido/mensaje desaparecido, aviso unico
de plazo, restricciones de cierre y resultado parcial. Suite `pnpm test`.
Pendiente repetir este escenario con Claude y Slack reales despues de la correccion.

### Fuera Del Cierre

Board-first de v1, skills o mapas de dominios de una empresa, infraestructura de
plantillas/despliegues y publicacion de MCP remoto/OAuth para otros clientes no
son requisitos de cierre de v2. Tampoco se exige un programa de soak como fase
independiente; si pruebas reales descubren fallos de estabilidad, se corrigen.

El documento historico conserva pruebas y decisiones pasadas para consulta.
No convierte esas decisiones en requisitos actuales.
