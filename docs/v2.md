# regent v2 — arquitectura

**Estado:** `ask` y `patch` validados en real (Slack + PR); flujo de tarea, soak y fases 3-4 pendientes · **Rama:** `v2` · **Fecha:** 2026-09-06

v1 es un pipeline *tracker-first*: un card entra a una columna, un rol con herramientas recortadas ejecuta una fase, escribe en el card y lo mueve. Funciona, pero en uso real lo que el equipo quiere es otra cosa: **un colega con todo el contexto del repo y los datos, al que le hablas desde el chat, responde en el hilo, parchea lo chico ahí mismo y solo abre tracker cuando vale la pena**. v2 invierte el diseño: el chat es la interfaz, el agente es uno solo y tiene todas las herramientas, y el tracker (card, sala, PR) es una herramienta que el agente llama cuando corresponde.

---

## 1. Qué falló en v1 (y qué no)

Diagnóstico sobre un caso real, verificado contra el hilo, la sala, el card y `log/events.jsonl`:

| Síntoma que el equipo vio | Causa raíz | Dónde |
|---|---|---|
| Seis mensajes para asignar la tarea a una persona, ninguno funcionó | intake no puede llenar propiedades `people` y no le dice al modelo por qué | `intake.ts` |
| Dos mensajes de texto plano ("quiero otra opción", "ejecuta la C") sin respuesta | sin `@rol` van como *intervención* al tab de terminal del agente — que ya había terminado; cero feedback | `terminal.ts:151-166` |
| `@dev` planificó en vez de ejecutar; el handoff dev→dev se negó en silencio | `can_trigger` niega y solo loguea, no publica en la sala | `server.ts:431-434` |
| "No tuve acceso a `git log`" | el answerer corre `claude -p --allowed-tools Bash(git log:*)`; el archivo vivía en un submódulo y hacía falta `git -C <sub> log`, que no matchea el prefijo → denegado sin `gh` de respaldo | `answer.ts:21,32-34` |
| Card con cada sección duplicada | `**Actualización desde Slack:**` por mensaje sin agente vivo; el dev re-planeó sin regla; segunda `## Implementación` tras auto-corrección; `handleTerminal` sin idempotencia (dispara por el merge del PR **y** por el eco de Notion) | `server.ts:1340,518,720`, `agents/dev.md:18` |
| Un canal entero para un fix de un archivo | intake solo bifurca pregunta/tarea; toda tarea = card + sala, sin compuerta de tamaño | `intake.ts:86`, `server.ts:1266` |

**Lo que no falló:** el modelo. El PM encontró la causa real en 2.5 min y el dev sacó un PR correcto en 2 min. Calidad de prompts y frescura del workspace tampoco fueron factores.

Ranking por impacto: (1) **fallos silenciosos** — el bot parece sordo y la gente reenvía; (2) **diseño workflow-first** — toda tarea nace con card + sala; (3) **split de roles + allowlists** — procesos separados con herramientas recortadas que el modelo no sabe que no tiene.

## 2. Principios de v2

1. **Un agente, todas las herramientas.** No hay pm/dev/qa como procesos; son *skills* que el mismo agente invoca. La herramienta que "no debe usar" se frena con hooks duros (§7.7), no con allowlists que el modelo no ve.
2. **El chat es la UI; el tracker es una herramienta.** Card, sala y PR se crean cuando el agente (bajo política) decide que vale la pena — nunca como paso obligatorio de entrada.
3. **Cero silencio.** Todo mensaje recibe un acuse en ≤ 3 s y un resultado o un error explicado. Toda acción denegada se publica con el motivo.
4. **Compuerta de tamaño explícita.** S se resuelve en el hilo (respuesta o PR). M/L crean card y, según política, sala. El límite es código, no criterio del modelo.
5. **Una conversación = una sesión.** Hilo de Slack, DM, conversación MCP o sala mapean a **una** sesión de `claude` que se reanuda (`--resume`); el contexto no se pierde entre mensajes.
6. **Idempotencia en cada efecto externo.** Escrituras a Notion por sección (upsert), PR por rama, proyecto por paso; eventos entrantes deduplicados por id.
7. **regent nunca toca credenciales de Anthropic.** Usa el binario `claude` sin modificar con el login o la API key del operador (§3).
8. **Lo que v1 aprendió se conserva** (§8): datos ≠ instrucciones, activación explícita, worktree por repo, base fresca, intake que lee el hilo completo, preguntas abiertas nunca disparan trabajo.

## 3. Modelo de autenticación y términos

Condiciona todo lo demás, así que va primero. Verificado contra los términos vigentes (2026-09): *Consumer Terms* §2 y §3, *Claude Code — Legal and compliance* y *Agent SDK — overview*.

| Modo | Quién | Cómo autentica | Qué dicen los términos |
|---|---|---|---|
| **indie** | una persona, su propio Slack, su propio servidor | `claude login` con su Pro/Max en la máquina donde corre regent | Permitido: *"an end user signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code"*. Condición: **un solo humano** da instrucciones. Los límites del plan asumen *"ordinary, individual usage"*. |
| **equipo** | varias personas por Slack | `ANTHROPIC_API_KEY` en el entorno del servidor (Commercial Terms) | Permitido: *"configuring an API key in a development environment, secrets manager, or machine image for use by the customer's own authorized users"*. Facturación por consumo. |

Prohibido en ambos modos, y por eso regent no lo hace: leer, copiar o proxyar tokens OAuth (`~/.claude/.credentials.json`, `CLAUDE_CODE_OAUTH_TOKEN` de otra persona), ofrecer login de claude.ai dentro de regent, modificar el binario, usar el Agent SDK con credenciales de suscripción.

Consecuencias de diseño:

- **Motor = binario `claude` (headless), no el Agent SDK.** El SDK exige API key; el binario acepta ambos modos. regent lo lanza como subproceso con `-p --output-format stream-json`.
- **Sin `--bare`.** Bare mode no usa el login de suscripción y además no carga `CLAUDE.md`, skills ni `.mcp.json` del repo — y ese contexto es el producto.
- **Guardia de arranque.** `auth.mode: indie|team`. En `indie`, si la allowlist de usuarios (Slack + MCP) tiene más de una persona y no hay `ANTHROPIC_API_KEY`, el server no arranca y explica por qué. En `team`, sin API key no arranca.
- **Consumo visible.** Cada `result` de stream-json trae `total_cost_usd` y `usage`; se guardan por run/usuario/día (§7.4). En `team` sirve para topes; en `indie` para saber cuándo se acerca al límite del plan.

### 3.1 Contexto: qué persiguió Anthropic en 2026 y qué no

Enero–febrero: bans de cuentas por reuso de tokens OAuth y pedido legal a un proyecto open source para que dejara de usar keys de Pro/Max fuera del binario. Abril: las suscripciones dejan de cubrir agentes autónomos de terceros. Mayo–junio: se anuncia un **Agent SDK credit** mensual por cuenta en Pro/Max/Team/Enterprise que cubre `claude -p`, GitHub Actions y *"third-party apps that authenticate with your Claude subscription through the Agent SDK"* — no compartible entre personas; el rollout quedó pausado el 15 de junio "pending further development", así que su vigencia se verifica al implementar, no se asume.

Lo que se persiguió fue **intermediar credenciales** (extraer el token, ofrecer login propio, una cuenta para muchos), nunca lanzar el binario oficial con el login de uno mismo. regent v2 hace lo segundo por construcción.

### 3.2 Blindaje del proyecto

El setup y el arranque muestran una advertencia para `indie`: compartir la cuenta o
permitir que otras personas usen la suscripción mediante el bot puede incumplir los
términos y causar suspensión o terminación del acceso (baneo). El aviso no permite
el uso compartido: se mantiene la guardia de un único usuario. Pro/Max individual no
requiere API key. Referencia: [Consumer Terms §2 y §12](https://www.anthropic.com/legal/consumer-terms).

Tres reglas que se aplican al repo, no al runtime, para que nadie pueda confundir a regent con un intermediario de credenciales:

1. **README con la regla de autenticación explícita**, en una sección propia y al inicio: `indie` = tu propio login de Claude en tu máquina, **un solo humano** dando instrucciones; `team` = `ANTHROPIC_API_KEY`. Con la cita de los términos que lo permite y la guardia de arranque que lo hace cumplir. La documentación es parte de la evidencia de intención.
2. **Branding.** El producto se llama regent. Nunca "Claude Code <algo>" ni "Claude Code Agent" en nombre, descripción, logo o app de Slack; "Powered by Claude" es lo permitido por las guías del Agent SDK. La app de Slack y el conector MCP se describen como regent.
3. **Política de contribuciones** (`CONTRIBUTING.md`): no se aceptan cambios que lean, copien, almacenen o reenvíen credenciales de Anthropic (`~/.claude/.credentials.json`, `CLAUDE_CODE_OAUTH_TOKEN` de terceros, tokens de sesión), que agreguen un "login con Claude" dentro de regent, que llamen a la API de Anthropic con credenciales de suscripción sin pasar por el binario, o que modifiquen el binario. Es lo único que convertiría el repo en un intermediario.

## 4. Arquitectura

```
                 ┌──────────────────── adaptadores ────────────────────┐
  Slack (Bolt, Socket Mode, Agent messaging)  │  MCP remoto (Streamable HTTP + OAuth)  │  Notion webhook (board, opcional)  │  CLI local
                 └──────────────┬──────────────┴──────────────┬─────────┴──────────────┬──────────────┴──────┬────┘
                                │  Inbound{conversation_key, author, text, files}       │                     │
                                ▼                                                        ▼                     ▼
                        ┌───────────────────────────────── core ─────────────────────────────────┐
                        │ Conversations · Sessions · RunQueue · Policy (tamaño, sala, presupuesto)│
                        │ Tools MCP interno: status · ask_human · create_task · update_task ·      │
                        │                    open_pr · create_project · cancel                    │
                        │ Store SQLite: conversations, sessions, runs, events, tasks, idem_keys,   │
                        │               usage, gates                                              │
                        └───────────────┬───────────────────────────────────┬────────────────────┘
                                        │ spawn                             │ regent-wt / gh
                                        ▼                                   ▼
                          ┌──────── runner ────────┐            ┌──────── workspace ────────┐
                          │ claude -p --resume …   │  cwd  ───► │ checkouts compartidos (ro) │
                          │ stream-json → eventos  │            │ worktrees agent/<id> (rw)  │
                          │ SIGINT/SIGTERM         │            │ refresh · sync · PRs       │
                          └────────────────────────┘            └────────────────────────────┘
                                        │
                                        ▼  carga solo (cwd): CLAUDE.md · .claude/skills · .mcp.json (DB, logs…) · hooks
                                        ▼  + plugin regent (--plugin-dir): skills plan/implement/qa/project · hooks duros
```

Un proceso Node (`node src/server.ts`, ESM, sin build — igual que v1). Lo público es el túnel: `/mcp`, `/oauth/*`, `/.well-known/*`, `/webhooks/*`. Slack no necesita ingreso (Socket Mode). El server escucha en `127.0.0.1`.

### 4.1 Core

**Conversation.** Clave `(adapter, scope, thread)`: `slack:C123:1788424575.808199`, `slack:D456` (DM), `mcp:<user>:<conv_id>`, `notion:<page_id>`. Estado: `idle | queued | running | waiting_human | interrupted`. Guarda `session_id` de `claude`, cwd, `repo`, `task_id` si ya hay card, `room` si ya hay sala, último `run_id`.

**Session.** Una por conversación. La primera vez se lanza sin `--resume` y se captura `session_id` del evento `system/init`; después siempre `--resume <session_id>`. `--resume` funciona desde cualquier cwd en la misma máquina (Claude Code ≥ 2.1.223). Reset explícito (`nuevo`, `reset`) o por inactividad (`session.idle_reset_hours`, default 24 en DMs, nunca en hilos).

**RunQueue.** FIFO por conversación (un run a la vez por sesión — `--resume` no admite dos escrituras concurrentes al mismo transcript). Semáforo global `limits.max_concurrent_runs` (default 3, por CPU/RAM de la caja). Un mensaje que llega mientras corre se **encola como follow-up** y se anuncia ("en cola, lo leo al terminar") — nunca se descarta. `stop` o el botón de Slack interrumpen (§5.5).

**Policy.** Reglas duras en código, guía en el prompt:

- `small_fix`: `max_files: 5`, `max_lines: 150`, `deny_paths: ["**/migrations/**", "**/schema*", "infra/**", ".github/**"]`, `require_tests_pass: true` (si el repo tiene comando de test declarado). `open_pr` la aplica; si no cumple, devuelve un rechazo estructurado y el agente debe `create_task`.
- `room: never | on_task | always` (default `on_task`: se abre sala al crear card M/L).
- `track_small_fixes: none | digest | card` (default `digest`: los PRs S se listan en un canal de resumen; `card` crea un card en Done para trazabilidad).
- Presupuestos por run y por usuario/día (§7.4).

**Tools MCP interno.** Un MCP Streamable HTTP servido por el mismo proceso en `127.0.0.1`, inyectado al `claude` hijo con `--mcp-config` y un bearer **por run** (así el core sabe qué conversación llama). El agente no tiene `ncard` en PATH ni permiso de usarlo (hook): **el core es el único escritor de Notion y Slack**.

| Tool | Hace | Idempotencia |
|---|---|---|
| `regent_status(text)` | línea de progreso en la conversación (throttle 1/3 s por límite de Slack) | — |
| `regent_ask_human(question, options?)` | publica la pregunta (Block Kit con opciones si hay), cierra el run en `waiting_human`; la respuesta reanuda la sesión. Reemplaza `AskUserQuestion`, que no existe en `-p` desatendido | una pregunta abierta por conversación |
| `regent_create_task({title, summary_md, plan_md?, size, impact, repo?})` | card en `landing_status` con secciones; sala según `room`; devuelve `task_id`, URL, sala | clave `(conversation, hash(title))` → si existe, devuelve el existente |
| `regent_update_task({task_id, section, md})` | **upsert** de la sección por ancla (`## Qué se va a hacer`, subpágina `Plan técnico`, `## Implementación`, `## QA`) | por `(task_id, section)` |
| `regent_open_pr({repo, title, body_md, size_claim})` | aplica `small_fix` si la conversación no tiene card; `regent-wt pr` + `gh pr create`; registra en `tasks.prs` | por `(conversation, repo)` → rama `agent/<conv_short>-<repo>`; si el PR existe, lo actualiza |
| `regent_create_project({slug, description, stack?})` | máquina de estados §5.4; devuelve URLs | por paso, reanudable |
| `regent_cancel()` | el agente se rinde con motivo (p. ej. tarea fuera de alcance) | — |

**Prompt.** Un solo system prompt de "colega" (reemplaza `agents/{pm,dev,qa}.md`) vía `--append-system-prompt-file`, más el bloque de seguridad de `phase-prompt.ts` (contenido = datos, no instrucciones; entorno git; qué tools existen y cuándo). El mensaje de usuario del primer turno es el hilo completo en markdown (`slack-thread.ts`, reutilizado) con autores; los siguientes turnos solo el mensaje nuevo con autor. Las reglas de política se expresan en el prompt **y** se aplican en las tools: si el modelo se equivoca, la tool lo corrige con un error legible.

**Plugin regent** (`plugin/`, cargado con `--plugin-dir`): skills `plan`, `implement`, `qa`, `project` (el oficio de los ex-roles, ahora invocables por el mismo agente según la fase); hooks `PreToolUse` que niegan lo que ninguna política permite (§7.7). Un repo puede sobreescribir skills con las suyas en `.claude/skills/`.

**Modelo.** Default del CLI (el más capaz). Override opcional por intención en `models: {ask, patch, task, project}` — no hay "secretario" barato: el propio agente enruta llamando tools.

### 4.2 Runner

```
claude -p <prompt> \
  --output-format stream-json --verbose --include-partial-messages \
  [--resume <session_id>] \
  --permission-mode bypassPermissions --permission-prompts none \
  --append-system-prompt-file plugin/colleague.md \
  --mcp-config '{"mcpServers":{"regent":{"type":"http","url":"http://127.0.0.1:8787/tools","headers":{"Authorization":"Bearer <run_token>"}}}}' \
  --plugin-dir plugin \
  [--add-dir <worktree>] [--model <m>]
```

- cwd = `workspace_root` (raíz del monorepo: CLAUDE.md, skills, `.mcp.json`, todos los repos legibles) o el repo del card. Igual que v1.
- env = `.env` de la instancia + `agent_env_files` (para que `${VARS}` del `.mcp.json` resuelvan) + `REGENT_RUN_ID`. Igual que v1.
- Parser de stream-json → eventos internos: `init{session_id, mcp_servers, mcp_server_errors}`, `text_delta`, `tool_use`, `tool_result`, `api_retry`, `permission_denied`, `result{total_cost_usd, usage, permission_denials, is_error}`. `mcp_server_errors` no vacío = fallo de arranque que se reporta, no se ignora.
- Cancelación: `SIGINT` (cierra el turno, hasta `cancel.grace_sec` = 60) → `SIGTERM` (exit 143, el turno queda incompleto pero la sesión se reanuda).
- Timeout por intención (§7.3) → misma secuencia + mensaje.
- `--permission-mode auto` (clasificador) queda como alternativa a evaluar por instancia; el default es bypass + hooks porque un agente desatendido no puede contestar prompts.

### 4.3 Adaptadores

**Slack** (reemplaza `chat-slack.ts` + `chat.ts` + los handlers Slack de `server.ts`):

- Bolt Socket Mode (sin ingreso público; sirve para indies detrás de NAT).
- Migración al **Agent messaging** de Slack: sesión de agente por hilo *en canales* (no solo DMs), `agents.sessions.setStatus` (`processing` → `active` explícito), `chat.startStream/appendStream/stopStream` para el texto en vivo, botón *stop* → `regent_cancel`, `assistant.threads.setSuggestedPrompts` con 3-4 prompts fijos. Migración irreversible desde `assistant.threads.*`.
- Eventos: `app_mention` (arranca conversación en el hilo), `message.*` con `thread_ts` de una conversación activa (follow-up sin mención), `message.im` (DM = conversación privada), `block_actions` (botones de compuertas §5.3), `agent_session_stopped`.
- Dedupe por `event_id` en SQLite (Slack reintenta; Socket Mode también reenvía sobres).
- `gatherThread` y `threadToMarkdown` de v1 se reutilizan tal cual (bots, adjuntos, archivos, canales privados).
- Salas: `#task-<slug>` solo bajo `room` (§4.1). La conversación se **re-clava** a la sala (misma sesión, nueva clave) y el hilo de origen recibe el puntero.
- Caras por rol (`setup-slack-roles.ts`) desaparecen: un solo bot.

**MCP remoto** (nuevo, `src/mcp-remote.ts`):

- Streamable HTTP en `/mcp` con `@modelcontextprotocol/sdk` (`createMcpHandler` + `requireBearerAuth` + `mcpAuthRouter`; confirmar nombres contra la versión del SDK al implementar — la 2.x separa paquetes).
- OAuth 2.1 con **Dynamic Client Registration + PKCE S256**, que es lo que claude.ai usa de fábrica para conectores custom. Metadatos RFC 8414/9728 en `/.well-known/*`, `401` con `WWW-Authenticate: Bearer resource_metadata=…`, redirect `https://claude.ai/api/mcp/auth_callback` (y loopback para Claude Code). Endpoints de OAuth responden en < 10 s (límite de Claude).
- **Identidad = Sign in with Slack (OIDC)** del workspace configurado: `ProxyOAuthServerProvider` del SDK delega el consentimiento a Slack; regent verifica `team_id` y la allowlist opcional y emite sus propios tokens (refresh rotativo). Una identidad para Slack y MCP; el resultado de un run largo puede llegar al DM de Slack de esa misma persona.
- Tools: `ask(question, repo?)`, `patch(request, repo?)`, `create_task(...)`, `create_project(...)`, `status(run_id)`, `cancel(run_id)`, `conversations()`. `ask`/`patch` responden de forma síncrona hasta `mcp.sync_timeout_sec` (default 60; el timeout real de claude.ai por tool no está documentado — medir) y si no terminaron devuelven `{run_id, partial}`; el resto llega por `status` y por DM de Slack.
- Disponible en Claude web, Desktop y mobile para Free/Pro/Max (cada usuario lo agrega en *Customize → Connectors*) y org-wide en Team/Enterprise (lo agrega un Owner). Slack mobile ya cubre móvil desde la fase 1; el conector es para quien prefiere Claude.
- Opcional: allowlist del egress de Anthropic (`160.79.104.0/21`) en el túnel/WAF.

**Notion webhook** (heredado, opcional): `notion.board_triggers: false` por defecto en v2. Si se activa, arrastrar un card a una columna con `trigger` crea/reanuda la conversación `notion:<page_id>` y corre la skill de esa fase — compatibilidad con quien quiera board-first. Comentarios con `@mención` al bot también entran como mensajes de esa conversación. El eco de Notion (`skip_own_echo`) deja de disparar efectos: solo actualiza estado.

**CLI local** (`regent ask "…" [--repo]`, `regent tail <run_id>`, `regent runs`): para el operador, mismo core, salida por stdout. Reemplaza herdr/tmux como forma de "mirar" un agente.

### 4.4 Workspace

`workspace.ts` + `regent-wt` se reutilizan tal cual: `scanRepos` (3 niveles, submódulos, auto-clone), checkouts compartidos solo lectura con `refreshShared` (cada hora y al lanzar), worktrees `agent/<id>` desde `origin/<base>` recién traído, `syncWorktreeWithBase` (conflicto → se marca al agente como lo primero), PR por repo, limpieza por registro, aviso de PR en `CONFLICTING`. Cambios: el `<id>` del worktree es la conversación (no el card), y la limpieza corre al cerrar la conversación o al mergear todos sus PRs.

### 4.5 Store

SQLite en `state/regent.db` (`node:sqlite`, sin flag desde Node 22.13 — confirmar versión en la caja; fallback `better-sqlite3`). Reemplaza `log/*.json` y el estado en memoria que se perdía al reiniciar.

| Tabla | Clave | Para qué |
|---|---|---|
| `conversations` | `key` | estado, `session_id`, cwd, repo, `task_id`, `room`, `last_run_id`, `updated_at` |
| `runs` | `run_id` | conversación, intención, inicio/fin, estado, `exit_code`, `cost_usd`, `usage`, `error` |
| `events` | autoinc | `(run_id, ts, type, payload)` — el transcript por run (lo que antes era `agent-*.out`) |
| `inbound` | `(adapter, event_id)` | dedupe de eventos entrantes |
| `tasks` | `task_id` | card, secciones escritas, PRs, sala, gate actual |
| `gates` | `(task_id, gate)` | `pending | approved | changes | canceled`, quién, cuándo |
| `projects` | `slug` | paso actual de la máquina de estados, URLs |
| `usage_daily` | `(user, day)` | costo/tokens acumulados |
| `idem_keys` | `key` | efectos externos ya realizados (`create_task`, `open_pr`, digest) |

`log/events.jsonl` sigue existiendo como log de decisiones del server (formato v1), rotado; ya no es fuente de estado.

## 5. Flujos

### 5.1 Pregunta en un hilo

1. `@bot ¿por qué la oferta X no muestra el badge verde?` → adapter Slack → `Inbound`.
2. Dedupe `event_id`; `conversations.get_or_create(slack:C:ts)`; `setStatus(processing)` (≤ 3 s).
3. `RunQueue.enqueue(intent=ask)`. Si hay cupo, `Runner.spawn` con el hilo completo como prompt (primera vez) o solo el mensaje (`--resume`).
4. El agente lee código (`Read/Grep/Glob/Bash git`, incluidos submódulos) y datos (MCP del repo). Texto en vivo → `appendStream`; `regent_status` para hitos.
5. `result` → `stopStream`, `setStatus(active)`, run cerrado con costo. Si el agente detecta que es un fix S, **ofrece** hacerlo ("¿lo arreglo? es un archivo") — no lo hace sin pedirlo, salvo que el mensaje ya lo pidiera.
6. Follow-up en el mismo hilo (sin mención) → paso 2 con `--resume`.

### 5.2 Fix S en el hilo → PR

1. `@bot arregla el color del badge de estado activo`.
2. Igual que 5.1 hasta que el agente decide cambiar código: `regent-wt add <repo>` (worktree desde `origin/<base>` fresco), edita, corre tests si el repo declara comando.
3. `regent_open_pr` → Policy `small_fix`: cuenta archivos/líneas del diff, chequea `deny_paths` y tests. Si pasa: `gh pr create`, registra, publica link en el hilo. Si no pasa: devuelve `{refused, reason, suggestion: create_task}` y el agente explica y crea card (5.3).
4. `track_small_fixes: digest` → línea en el canal de resumen. El merge del PR se detecta como en v1 (webhook `gh` + poll) y se anuncia en el hilo; el worktree se limpia.

### 5.3 Tarea M/L → card → compuertas → PR

1. El agente juzga M/L (o `open_pr` lo rechazó): `regent_create_task({size, impact, summary_md})` → card en `landing_status`, secciones escritas **una vez**; con `room: on_task` se crea `#task-<slug>`, se invita al solicitante, el hilo de origen recibe el link y la conversación se re-clava a la sala.
2. Skill `plan` → `regent_update_task(section: plan)` (subpágina técnica) + resumen en la sala + botones **Aprobar plan · Pedir cambios · Cancelar**. Run termina en `waiting_human`; `gates(task, plan_review) = pending`. Sin `@rol`: el gate es un botón. Un plan con preguntas abiertas **no muestra Aprobar**: muestra las preguntas y espera respuestas (regla de v1).
3. `block_actions` → `gates = approved` (quién, cuándo) → run con `--resume` y skill `implement` en worktree → `regent_open_pr` (sin límite `small_fix` porque hay card) → sección `## Implementación` (upsert) + link en sala + botones **Probado ✓ · Falla**.
4. `Falla` + texto → run con skill `qa`/`implement` sobre el mismo worktree; el PR se actualiza (mismo `open_pr`, misma rama). `Probado` → espera merge; merge de **todos** los PRs → card a `pr_merged_moves_to`, digest de la sala al card (una vez, por `idem_keys`), sala archivada, worktrees limpios.
5. Vía rápida (v1): esfuerzo S + impacto bajo + cero preguntas + plan inequívoco → el agente puede saltar el gate de plan si `policy.fast_track: true`; el botón de QA sigue.

### 5.4 Mini-proyecto

`regent_create_project({slug, description, stack})` corre una máquina de estados **por paso, reanudable**, con credenciales de la organización en el servidor (el solicitante nunca toca GitHub/Vercel/Supabase):

```
repo_created → scaffolded → db_provisioned → deployed → dns_ready → announced
```

- `repo_created`: `gh repo create <org>/<slug> --template <template>`; clonado a `REPO_PATH`.
- `scaffolded`: skill `project` genera lo pedido dentro del template (Nuxt/Next + Supabase client, auth mínima, README con "cómo pedir cambios"); PR inicial o commit directo según `projects.first_commit`.
- `db_provisioned`: `supabase projects create` (o Neon) + secretos al proyecto de Vercel.
- `deployed`: `vercel link/deploy --prod`.
- `dns_ready`: CNAME `<slug>.<projects.domain>` vía API del DNS.
- `announced`: URLs en la conversación; card opcional.

Cada paso graba en `projects` antes de avanzar; un fallo reporta el paso y `create_project` se puede reintentar sin duplicar. Cambios posteriores al proyecto entran como 5.1/5.2 con `repo=<slug>`.

### 5.5 Mensaje mientras corre · stop

- Texto plano en una conversación `running` → `inbound` + follow-up en cola: "📥 lo tomo al terminar". Al cerrar el run actual, el siguiente arranca con `--resume` y ese mensaje. Nunca se tipea en un proceso vivo.
- `stop`/`para` o el botón de Slack → `SIGINT` → si no cierra en `grace_sec`, `SIGTERM` → "⏹️ detenido; la sesión sigue, escribe *continúa*". Follow-ups en cola se conservan.
- Mensaje con `@bot` en un hilo con conversación `waiting_human` → se trata como respuesta a la pregunta abierta (reanuda).

### 5.6 Desde Claude Desktop / mobile (MCP)

1. Usuario agrega el conector (`https://<host>/mcp`) → OAuth DCR → consentimiento en Slack → token.
2. `ask("¿cuántas empresas activas hay?")` → `conversations.get_or_create(mcp:<user>:<conv>)` → run síncrono hasta `sync_timeout_sec`.
3. Terminó → respuesta directa. No terminó → `{run_id, partial, hint: "status(run_id)"}`; al terminar, además DM de Slack al usuario con el resultado.
4. `patch` igual, con `small_fix`; si se rechaza, la respuesta trae el motivo y `create_task` como siguiente paso.

### 5.7 Board-first (compatibilidad v1)

Con `notion.board_triggers: true`: arrastrar a `Planning` → conversación `notion:<page>` + skill `plan` → botones en la sala (o comentario con las opciones si no hay sala) → igual que 5.3 desde el paso 2. `@bot` en un comentario de Notion = mensaje de esa conversación. Se mantiene para boards existentes; no es el camino recomendado.

## 6. Ciclo de vida de un run (contrato)

| Momento | Obligación |
|---|---|
| ≤ 3 s de recibido | acuse visible (`processing` en Slack; respuesta inmediata o stream en MCP) |
| cada ≤ 60 s mientras corre | algo visible cambió (stream, `regent_status`) o se publica "sigo trabajando: <última tool>" |
| al terminar | resultado, o error con causa y qué hacer |
| acción denegada (tool, hook, política) | mensaje con motivo y alternativa |
| reinicio del server | runs `running` → `interrupted`; mensaje en cada conversación afectada; `continúa` reanuda |

Este contrato es lo que v1 no tenía y explica la mayor parte de "se siente tonto".

## 7. Robustez

### 7.1 Idempotencia

- Entrantes: `inbound(adapter, event_id)` — Slack `event_id`, Notion `id` de evento/comentario, GitHub `delivery_id`, MCP `request_id`.
- Notion: una sección = un ancla; `update_task` reemplaza el bloque entre ancla y siguiente ancla. `ncard` gana `upsert-section`. Nada se *appendea* dos veces.
- PR: rama determinista por `(conversación, repo)`; si existe, se hace push a la misma y `gh pr edit`.
- Efectos únicos (`create_task`, digest, archivar sala, mover card por merge): `idem_keys` se escribe **antes** de ejecutar; un reintento encuentra la clave y devuelve el resultado anterior.
- `handleTerminal` (merge → mover + digest + archivar) se dispara solo desde el detector de merge; el eco de Notion solo sincroniza estado.

### 7.2 Concurrencia y backpressure

- Un run por conversación; `max_concurrent_runs` global; cola con posición visible.
- Lock por worktree: dos conversaciones no comparten worktree; dos runs de la misma conversación no coexisten.
- `refreshShared` no corre mientras haya un run usando ese checkout (v1 ya evita tocar sucio/divergido; v2 además espera).

### 7.3 Timeouts

| Intención | `max_run_sec` default | Al vencer |
|---|---|---|
| ask | 600 | SIGINT → SIGTERM; "tardó más de 10 min; ¿acoto la pregunta?" |
| patch | 1800 | igual; el worktree queda para reanudar |
| task (fase) | 3600 | igual; la sala lo sabe |
| project (paso) | 900 por paso | paso marcado `failed`, reintentable |

Todo configurable por instancia. Un run que no emite eventos en `stall_sec` (300) se considera colgado aunque no haya vencido.

### 7.4 Presupuestos

- Por run: `--max-turns` no se usa (corta a mitad de trabajo); se usa el timeout + `budget.max_cost_usd_per_run` (solo modo `team`, desde `result.total_cost_usd` del run anterior + estimación por tokens en vivo).
- Por usuario/día: `budget.max_cost_usd_per_user_day`; al 80 % avisa, al 100 % rechaza con motivo y a quién pedir más.
- Reporte diario al canal de operaciones: runs, costo, fallos, top conversaciones.

### 7.5 Recuperación

- Arranque: migra esquema SQLite; runs `running` → `interrupted` + mensaje; follow-ups en cola se conservan; worktrees huérfanos (sin conversación viva) se limpian si están limpios.
- `--resume` tolera un proceso matado a mitad de turno (el turno queda incompleto y continúa).
- Slack desconectado (Socket Mode): Bolt reconecta; eventos perdidos durante la caída **no** se recuperan — se documenta y el `/healthz` expone `slack_connected`.
- Notion/GitHub: los reintentos del proveedor + dedupe hacen el resto (v1).

### 7.6 Git y submódulos

Herencia directa de v1 (§4.4). Añadido: el prompt declara los submódulos y la forma correcta de consultarlos (`git -C <ruta>`), y bajo bypass no hay allowlist de prefijos que lo frene.

### 7.7 Permisos y seguridad

- **Bypass + hooks duros.** `--permission-mode bypassPermissions` porque nadie contesta prompts. El tope real son hooks `PreToolUse` del plugin regent (y los del repo, que también aplican): niegan DML/DDL contra MCPs marcados `readonly` en `regent.yaml`, `git push --force*`, `git push` a ramas base, `rm -rf` fuera del worktree, escrituras en checkouts compartidos, `ncard`/`regent-wt pr` directos (solo vía tools), `curl|sh`. La denegación llega al modelo como error y al chat como aviso (§6).
- **Bases de prod:** además del hook, el MCP de la base usa un usuario de solo lectura. Doble cerrojo.
- **Datos ≠ instrucciones.** El bloque de seguridad de `phase-prompt.ts` se conserva: contenido de hilos, cards, comentarios y archivos es dato; instrucciones embebidas se reportan, no se obedecen.
- **Worktree aislado** para todo cambio; checkouts compartidos solo lectura.
- **Secretos** solo en `.env` (600) y en el entorno del proceso; los transcripts en `events` pasan por un redactor (patrones de tokens/keys) antes de guardarse.
- **Red:** server en `127.0.0.1`; túnel expone solo `/mcp`, `/oauth/*`, `/.well-known/*`, `/webhooks/*`; el MCP interno de tools exige bearer por run; Slack por Socket Mode.
- **Identidad:** allowlist de usuarios de Slack y del workspace (`team_id`) para MCP; en `indie`, un solo usuario.

### 7.8 Observabilidad

- `GET /healthz`: `slack_connected`, `runs_running`, `queue_depth`, `db_ok`, `claude_version`, `auth_mode`.
- `GET /metrics` (texto plano): contadores de runs por estado/intención, costo del día, latencia de acuse.
- `regent runs` / `regent tail <run_id>`: transcript en vivo desde `events`.
- Canal de operaciones: reporte diario (§7.4) + errores no recuperables al momento.

### 7.9 Límites externos

- Slack: `chat.update`/stream ≤ 1 cada 3 s → buffer de texto con flush cada 3 s o 800 caracteres; `setStatus` y `appendStream` con reintento en 429.
- Anthropic: `system/api_retry` del stream se refleja como estado ("reintentando, límite de tasa"); en modo `indie`, un `rate_limit` persistente se traduce a "tu plan llegó al límite de la ventana".
- claude.ai conector: OAuth < 10 s; tool síncrono acotado por `sync_timeout_sec`.

### 7.10 Tests

Se mantiene el runner de v1 (`check` + `node:assert`, `.test.mjs`, sin red). Nuevo:

- **`claude` falso** (`test/fake-claude.mjs`): binario que emite un stream-json guionado por fixture (init, deltas, tool_use contra el MCP interno, result). Permite probar runner, parser, cancelación, timeouts y el contrato §6 sin tokens.
- **Slack falso**: servidor HTTP que registra llamadas (`postMessage`, `startStream`, `setStatus`, `block_actions`) — el adaptador deja de ser la única pieza sin tests.
- **SQLite en temporal** por suite; migraciones probadas desde vacío y desde v1 (`log/*.json` → tablas).
- **Política**: `small_fix` con diffs sintéticos; `room`/`track_small_fixes`; presupuestos.
- **Workspace**: los tests con git real de v1 siguen.
- **Smoke opt-in** (`pnpm smoke`, necesita `claude` real): un `ask` sobre el propio repo y un `patch` trivial en un repo temporal.

solo para el transporte interno; el motor sigue siendo el binario `claude`. Las

de pruebas como argv en `repos.test_commands`. `fast_track` queda desactivado por defecto.

identidad estable; si no puede localizarse, se detiene y requiere revisión operativa,
no se repite a ciegas. Los upserts de Notion preservan contenido fuera de sus anclas;
reemplazar sus hijos no es atómico y una interrupción puede dejar una sección parcial
hasta reintentar. Los avisos de Slack no prometen exactly-once.
